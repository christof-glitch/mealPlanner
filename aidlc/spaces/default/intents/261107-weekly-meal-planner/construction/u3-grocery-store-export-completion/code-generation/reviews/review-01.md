### Invariant Check Evidence

- **ADR-006/R-01–R-03:** `LockSnapshot` keeps IDs/selections + plan context (`ShoppingModels.kt`). `ShoppingListService.generateFromLockSnapshot` validates snapshot, re-resolves ingredients via injected `RecipeSourceBoundary.resolveIngredients` (no frozen ingredient fabrication), and returns typed `INVALID_SNAPSHOT`/partial outcomes with notes. `ShoppingListRules.evaluateRegenerationRequest` returns `CONFIRMATION_REQUIRED` and preserves the current edited list when `hasUserEdits` and regenerate is not confirmed. `ShoppingListStaleWarning.EXACT_TEXT` is exactly `"Meal plan modified. Grocery list not up-to-date. Press the Regenerate button."` and `ShoppingListStaleStatus` reflects it; service/regeneration flow does not auto-regenerate. Tests: `ShoppingListServiceTest`, `ShoppingListC4CompletionTest`.
- **R-02/BR3.5:** C4 owns projection via `ShoppingListRules.applyPresenceCheckBatch` (explicit operation, list/store scope checks, remap/unknown behavior). `StorePresenceUseCase` accepts only store + `PresenceCheckQuery` and returns `PresenceCheckBatchResult`; it does not mutate shopping items/aggregate. Ambiguous/no mapping/store-scope issues produce `UNKNOWN`/reasons (`NO_PRESENCE_PROJECTION`, `AMBIGUOUS_PRESENCE_MAPPING`, `STORE_SCOPE_MISMATCH`, edit/identity remap paths). Legacy `applyBatchPresenceToList` preserves `UNKNOWN_AFTER_EDIT_NO_MAPPING` and does not fabricate `PRESENT` for unresolved merged items. Minor seam gaps noted in findings.
- **FR8:** `StorePresenceStatus` includes `PRESENT\|NOT_FOUND\|UNKNOWN\|NOT_CHECKED`; C5 constrains mapped results to `PRESENT\|NOT_FOUND\|UNKNOWN`. No stock/quantity/guarantee fields in C5 result contracts. `StoreAvailabilityContractsTest` covers allowed statuses and mapped batch outcomes.
- **FR9/FR10/BR3.8/BR3.9:** `ShoppingListRules` merge is deterministic and keeps incompatible/uncertain cases separate; no fabricated quantities. `prepareCurrentExportState` exports current edited aggregate (filters removed items, uses current display/checked/quantity/availability). `ExportSeam.kt` defines inward seam (`ExportShoppingListUseCase`, `ShoppingListExportDto`, `ShareExportPort`, `SostoslistaOfficialExportPort`) with no Android intent types in domain; mandatory fallback instructions preserved. S-ostoslista official path is behind port and investigational. `ExportFallbackUseCase` legacy API remains compatible.
- **Export outcome mapping / no fabricated success:** `DefaultExportShoppingListUseCase` maps official `SUCCESS` → `ExportResultStatus.SUCCESS` + `ExportInvestigationOutcome.USED`; `NOT_SUPPORTED` → fallback + `NOT_FEASIBLE_CONFIRMED`; `UNAVAILABLE`/`FAILED_MAPPED` → fallback + `PARTIALLY_USED`; preferred official not attempted → fallback + `UNKNOWN`. Fallback coercion prevents a fallback path from reporting `SUCCESS`. Tests cover these cases.
- **NFR3/NFR4/NFR5:** Reviewed U3 domain code contains no hardcoded secrets, no account/auth, and no raw GPS coordinate storage/handling (store selection uses typed refs/suggestion statuses; nearest lookup is behind port). Diagnostics/messages are coarse/typed (`FallbackReason`, status enums, safe messages). Existing brownfield tests (`ShoppingListGenerationRulesTest`, `ApplyBatchPresenceToListTest`, `ExportFallbackTest`) remain present and passed in the U3-scoped run.
